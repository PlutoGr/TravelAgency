# Short memory (durable cache)
Box file `/home/box/shared/travelagency/work/memory.md`, heading «TravelAgency: short memory». Not in git.

A **small cache** of in-flight facts that must survive compaction or token loss. It is not a backlog and not a second board. **Board and GitHub remain the source of truth** for columns, labels and the backlog. This file is the single source for the row fields, the Sha cell, the `Waiting on` values, the `Question` field, the [Question guard](#question-guard), the `Last deploy:` line and the row lifecycle; other files link here.

## What it holds
One table (or short lists) with:

| Field | Required when | Meaning |
|---|---|---|
| Issue | always for a row | `#NN`, or `-` for a Dependabot / unowned PR row or the [repair row](#repair-row) |
| Stage / column | always | current `статус:*` (FSM state), or `Dependabot` / `repair` / PR label when Issue is `-` |
| PR | when a PR exists | number and URL |
| Sha | when a PR exists or was merged | the [Sha cell](#sha-cell) format |
| Agent | while a cloud agent run is live | agent id of the live run only ([agent rule](#row-lifecycle)) |
| Waiting on | always | the mechanical wait, one value of the [vocabulary](#waiting-on-values) |
| Question | always (`-` when none) | the open owner question or hold ([Question](#question)) |
| Next | always | the next concrete step (never empty) |

Under the table: a `Queue:` line while the merge queue is stopped, written by the [repair](../lifecycle/10-review-and-merge.md#repair-while-the-queue-is-stopped) (`stopped since run <id>; repair: re-run <id>` once the re-run has been started; `… | #NN` when a repair item is open; `… | repair row` only while a [repair row](#repair-row) ask is open and that re-run has not yet been started), removed when the queue resumes: on [repair-row observation](#repair-row) success or on a green Deploy / catch-up whose movement sha is the repair commit or a descendant of it ([Deploy wait](../lifecycle/events.md#deploy-wait), [repair](../lifecycle/10-review-and-merge.md#repair-while-the-queue-is-stopped)); and always a `Last deploy:` line (`<40-hex deployed sha> run <id>`), written and read only as the [Deploy wait](../lifecycle/events.md#deploy-wait) defines, so catch-up never depends on an artifact that has expired. Open owner questions and holds live only in the `Question` cells; live runs live only in `Agent`.

## Sha cell
One format for every row (product, non-product, Dependabot):
- Before merge: `head=<40-hex>` (the PR head; a `pr-checks` event matches it).
- After merge: `entry=<40-hex> fix=<40-hex|->`. `entry` = the merge that first left Разработка for Приёмка or the Deploy wait; `fix` = the latest fix merge during Приёмка, else `-` (always `-` on Dependabot and non-product rows without a fix).
- While a fix PR during Приёмка is open: `entry=<40-hex> fix=<40-hex|-> head=<40-hex>`; a `pr-checks` event matches `head`. On the fix merge keep `entry`, set `fix` to that fix merge and drop `head`; a fix merge is never written as `fix=-`.
- After a rollback the cell ends with ` rolled-back` until the match sha is deployed again ([rollback](#row-lifecycle)).
- **Match sha** = `fix` when set, else `entry`. The Deploy wait, the 60-minute catch-up (that PR's `mergedAt`), the rollback check and re-entry after a rollback all use the match sha.
- **Contains:** a sha is contained when it is the deployed sha or its ancestor (`git merge-base --is-ancestor <sha> <deployed sha>`), with the deployed sha read per [Deploy wait](../lifecycle/events.md#deploy-wait).

## `Waiting on` values
Only mechanical waits; an owner question or hold lives in [Question](#question), never here.
- `agent`: a live cloud agent run is the wait (its deliverable is the next step).
- `Automations`: Cursor Automations still running after a green `pr-checks` event (required checks are already finished; Automations are not required checks). On a [docs-only PR](../lifecycle/10-review-and-merge.md#ready-predicate) it waits only for that green event. Used when no live agent watches the PR (Dependabot). A red `pr-checks` result is not this wait.
- `Deploy`: merged, waiting for a green «Deploy to dev» whose deployed sha contains the match sha. Only a feature, bug-feature, non-product or Dependabot row waits on Deploy; never an epic.
- `issue #NN`: parked until issue #NN is Готово; `Next` = resume the parked step (for example acceptance of the parent, or taking a blocked child). Resumed by the [close procedure](board/columns/done.md) of #NN.
- `children`: an epic whose children carry the work: in Разбиение after the owner's yes to `approve split #NN` and until the first child is taken (while that `Question` is set, `Waiting on` stays `none` and no child is taken), and in В работе while any child is open. `Next` = В работе on the first take, the next child take, or the [epic demo](../lifecycle/13-epic-acceptance.md) on the last child close. Resumed by the take or by the child-close step of the [close procedure](board/columns/done.md). **Next child:** on every child close and in the full-demo gaps turn, take the next Очередь child of this epic in that same turn when the [parallel-work](../project.md#parallel-work) limits allow, subject to the [Question guard](#question-guard); when they do not, the next take is due on the wake that frees the stream (the close of the blocking item, or the merge it waited for). **Missed resume** (checked on every wake, used by [orchestrator §8](../orchestrator.md#8-never-stall) by link only): if every child is already Готово, start the epic demo on that wake; otherwise take the next Очередь child only when (1) no open child is past Очередь, (2) none is blocked by its own `issue #NN` or `Question`, and (3) the [parallel-work](../project.md#parallel-work) limits allow it (subject to the guard). A blocked take waits for the freeing wake; an epic may stay on `children` while a take is blocked that way.
- `none`: the `Next` step is actionable by the orchestrator now (once `Question` is `-`). Never use `none` for a mechanical wait.

The never-stall loop performs only `none` rows with `Question` = `-`; `issue #NN` and `children` rows are resumed by the close procedure (a missed resume is done at once: the issue is already closed, or the `children` missed resume above); the [repair row](#repair-row) is observed as defined there.

An “orchestrator review” is `none` with `Next` = full review. Use that shape only when the review can start now: a Dependabot PR whose Automations are still running stays `Waiting on` = `Automations` ([dependencies](dependencies.md)). Dependabot row: `Issue` = `-`, `Stage` = `Dependabot`, `PR`, `Sha` = `head=…`, `Waiting on` = `Automations`, `Next` = check Automations, then full review; after the switch `none` with `Next` = full review; after merge `Deploy` with `entry=… fix=-`.

## Question
`-`, or exactly one of:
- an owner question: `<question> (asked: <issue comment or chat>)`, with ` agent <id>` appended when a cloud run ended `RESULT blocked` on it (the reply goes to that run);
- stage approval: the value starts with exactly one of `approve BA #NN` (epic Бизнес-анализ), `approve epic architecture #NN` (epic Архитектура), `approve split #NN` (Разбиение), or legacy `approve feature BA #NN`. Do not set `approve feature BA #NN` on new work; a row that already has it stays in Аналитика. The usual ` (asked: chat)` may follow the token. Cleared only by the owner's yes to that stage ([owner stage approval](../orchestrator.md#owner-stage-approval)). A no or an edit request keeps the value and the column. For an epic token the section is reworked and the digest is sent again. Yes on legacy `approve feature BA #NN` then advances Аналитика;
- `epic demo` (the owner demo ask, [epic demo](../lifecycle/13-epic-acceptance.md));
- `create Status «Демо»` (the Project Status option is missing);
- the [repair row](#repair-row) ask;
- `hold: <reason>; resume: <condition>; restore «<column>»` for [Удержание](board/columns/on-hold.md).

Rules:
- **Blocks transitions:** by the [Question guard](#question-guard).
- **Answer:** an owner reply clears only the `Question` it answers (the [owner answer](../lifecycle/events.md#events) event); then re-evaluate the row and perform the pending step if its condition holds now ([Answer turn](#row-lifecycle)). A reply that does not answer it keeps it. A stage-approval token clears only on the owner's yes; a no or an edit request keeps it. The [repair row](#repair-row) ask is not cleared by a reply (including the owner's yes that starts the re-run): it ends only when the row is deleted by observation.
- **Re-ask:** the silence policy re-asks every non-empty `Question` except `hold:` on memory-refresh and the Monday audit only ([orchestrator §8](../orchestrator.md#8-never-stall)); a hold is listed in the weekly audit with its resume condition and never re-asked. While a [repair row](#repair-row) ask is open because the token cannot start workflows, keep re-asking until a new Deploy or re-run is visible; do not call `gh run rerun` from that answer turn.
- One `Question` per row. A second owner question about the same issue waits until the first is answered; a question about other work goes on that work's row.

### Question guard
Applies to every wake procedure before any column change, full review, merge, child take or stage start, on the row whose column changes or whose PR is reviewed or merged; a child take always includes the parent epic's row as well (aligned with [Разбиение](../lifecycle/05-epic-split.md) exit), not only when that take moves the epic's column. If that row's `Question` is not `-`, do only bookkeeping: the Sha cell, `Agent`, `Waiting on` (a met wait becomes `none`), `Next` = the pending step, and the [repair row](#repair-row) observation (it changes no column). Perform the pending step in the answer turn if it still holds (re-check then). A stage-approval token is not an exception: the column change and the child take wait for the owner's yes. Procedures that change a column, review or merge link here instead of restating it. The only exceptions:
- **(a)** reopening a child of an epic in Демо withdraws the epic's `epic demo` and moves the epic to В работе in that step ([close procedure](board/columns/done.md)); it is not an owner answer.
- **(b)** the recorded resume turn of a hold clears `hold:` on every row whose resume condition was met — that item itself, or the epic plus each child named in the epic hold comment — restores those columns and «Приоритет», then restarts each restored row in that turn ([Удержание](board/columns/on-hold.md)).

## Repair row
Created only for an owner ask of the [repair](../lifecycle/10-review-and-merge.md#repair-while-the-queue-is-stopped) (the token cannot re-run the failed run, or a server-side cause needs the owner's yes) or for the one re-run of a successful run whose artifact expired that the token cannot start ([Deploy wait](../lifecycle/events.md#deploy-wait)); it never rewrites another row. `Issue` = `-`, `Stage` = `repair`, `PR` = `-`, `Sha` = `-`, `Agent` = `-`, `Waiting on` = `none`, `Question` = the ask (cleared only by deleting the row), `Next` = observe `rerun <run id>` (or the new Deploy after the server change). The `Queue:` line points at `repair row` only until the re-run has been started; the yes turn rewrites it to `repair: re-run <id>` ([repair](../lifecycle/10-review-and-merge.md#repair-while-the-queue-is-stopped)). **Observation** (bookkeeping under the [Question guard](#question-guard); not run in the turn that created the row) runs on every later Deploy wake, every memory-refresh and every Monday audit. It branches on a **new attempt** after the ask (the re-run of the named run id started in the owner's yes turn, or a new «Deploy to dev» after the server change), never on the conclusion that opened the ask. No new attempt yet: keep the row and its `Question`; a clarifying reply keeps them too. New attempt queued or in progress: keep the row. New attempt succeeded: read its artifact, write [`Last deploy:`](#what-it-holds) under the run-id rule, delete the row, and remove `Queue:` when that movement sha is the repair commit or a descendant of it. New attempt failed or `cancelled` with no later run: delete the row and open the one repair item ([one re-run per failed run id](../lifecycle/10-review-and-merge.md#repair-while-the-queue-is-stopped)); retarget `Queue:` from `repair row` / `re-run <id>` to `#NN`; never re-ask or start a second re-run of that id.

## Row lifecycle
The single definition of how a row changes; stage and event files link here.
- **Create** when an item is taken, when a Dependabot `pr-checks` event is green ([dependencies](dependencies.md)), for a [repair row](#repair-row), when an issue is reopened (in the column its close comment names, [done](board/columns/done.md)), for a pre-take blocked child still in Очередь (`Waiting on` = `issue #NN`, `Next` = take the child; [Разбиение](../lifecycle/05-epic-split.md)), and for a global usage-block escalation (`Issue` = `-`, [orchestrator §8](../orchestrator.md#8-never-stall)).
- **Rewrite, keep the row:** every other transition (advance, owner question asked or answered, hold or resume, agent launch, finish or dismissal, wait cleared, rollback) rewrites `Waiting on`, `Question` and `Next` as needed (`Waiting on` and `Next` always written) and keeps the row while the issue is open.
- **Delete** only when the issue is closed and no Deploy wait remains, when a Dependabot row (`Issue` = `-`) is consumed by its green Deploy, or when a [repair row](#repair-row) is deleted by its observation rule (a new attempt after the ask succeeded, or failed / `cancelled` with no later run). Nothing else deletes a row; closed items then leave the file. Do not accumulate history.
- **Agent:** one live run per issue in `Agent` (finish or cancel a live run, for example a Крупная `Doc-` draft during Приёмка, before launching another). Launch: keep the mechanical wait (`Deploy`, `issue #NN`, `Automations`, `children`) and its `Next`; `Waiting on` = `agent` only when the agent is the wait. On the run's finish or error wake clear `Agent` and keep the mechanical wait. Block (a run ended `RESULT blocked` on an owner-needed question): `Question` = that question with ` agent <id>` (the reply address); keep the mechanical wait and its `Next`; only when `Waiting on` was `agent` it becomes `none` with `Next` = reply to that run. Answer turn: clear the `Question` it answers, except a stage-approval token, which clears only on the owner's yes ([Question](#question)). When the cleared `Question` had an ` agent <id>` suffix and `Next` is still the reply, reply to that run (or relaunch), set `Agent` to the resumed run and `Waiting on` = `agent`. When the cleared `Question` had an ` agent <id>` suffix and a mechanical wait is still pending, reply to that run, set `Agent` to the resumed run, and leave `Waiting on` and `Next` as they are. When bookkeeping already set `Waiting on` = `none` because a mechanical wait was met, perform that `Next` and record the resumed run only in `Agent`; the row-lifecycle write for that step is the final `Waiting on`. Never park a booked step by writing `agent` last.
- **Green Deploy containing the match sha** (a `Deploy` row): feature, bug-feature or non-product issue with a dev check → Приёмка, `Waiting on` = `none`, `Next` = finish acceptance; non-product issue without a dev check → close in this wake when its exit holds ([non-product work](../lifecycle/non-product-work.md)), else `Waiting on` = `agent` while a `Doc-` draft run is live, otherwise `none` with `Next` = the remaining step (publish the named page, check the criteria) and close; a closed issue or a Dependabot row → delete. Each move is subject to the [Question guard](#question-guard). Until that green Deploy a draft run is only in `Agent` and `Waiting on` stays `Deploy`.
- **Rollback after advance:** an open Приёмка row is rolled back only when the latest counted «Deploy to dev» run ([Deploy wait](../lifecycle/events.md#deploy-wait)) is an older sha that does not contain its match sha, and no newer counted run that will deploy a commit containing the match sha is queued or in progress (for a queued or in-progress run, the commit it will deploy is its `rollback_sha` when set, otherwise its head). **If `Question` is already set:** write only the Sha cell ` rolled-back` mark and set `Next` to redeploy after the current ask; do not replace the open `Question`; move the column on the answer turn when the [Question guard](#question-guard) allows it. **Otherwise:** column Разработка (label, Status and a status comment naming the rollback), Sha cell ` rolled-back`; `Waiting on` = `none` becomes `Deploy` with `Next` = re-enter Приёмка; a `Deploy` wait (a fix waiting for its Deploy) is kept unchanged; `agent` or `issue #NN` is kept, and when that wait is kept, save the previous `Next`. In that same turn, if no queued or in-progress «Deploy to dev» will deploy a commit that contains the match sha, set `Question` asking to redeploy the tip of `main` and (when the kept wait is not `agent` or `issue #NN`) `Next` = start «Deploy to dev» (tip of `main`, no `rollback_sha`) (a normal [Question](#question); the answer turn still starts that tip deploy even when `agent` / `issue #NN` kept their saved `Next`). The existing [Deploy wait](../lifecycle/events.md#deploy-wait) then restores Приёмка when that green movement sha contains the match sha: drop the mark; put the saved `Next` back with the kept wait when one was saved; otherwise keep the other wait (or `none` with `Next` = finish acceptance). Column moves are subject to the [Question guard](#question-guard) (the mark, saved `Next`, and redeploy `Question` are still written).
- **Read** on every wake, before new work, on the weekday memory-refresh routine (`travelagency-memory-refresh`), and at the weekly audit. A webhook is matched to `Waiting on`; no match exits without logging ([events](../lifecycle/events.md#webhook-match)).

## Relation to the FSM
The column on the issue is the state. Memory only records **waits and questions inside** that state so the orchestrator can resume. An owner question does **not** change the column; it sets `Question`.
