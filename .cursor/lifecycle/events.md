# Events and wakes
The orchestrator reacts to events instead of polling. Waiting state lives in [short memory](../elements/memory.md).

## Wake sources
The orchestrator runs only when one of these wakes it. Every timer in the rules is checked on the next wake from any source, except the owner re-ask: it runs only on weekday memory-refresh and the Monday audit.

| Wake | Source | What it carries |
|---|---|---|
| Cloud agent finished or errored | every cloud agent the orchestrator launches wakes it on finish or error; an agent **question ends the run** with `RESULT blocked` and that finish is the wake | agent id; read its report, branch, question or error |
| CI/CD webhook (safety net) | routine «TravelAgency CI/CD», fed by `.github/workflows/notify-cicd.yml` after «CI», «Deploy to dev» or «Secret scan» completes | workflow, conclusion, sha (run head), `deployed_sha` (Deploy: the commit actually deployed; set only on `success`, else empty; a hint only, [Deploy wait](#deploy-wait)), branch, run URL, run id |
| Memory refresh | routine «travelagency-memory-refresh» (weekday daily refresh) | refresh [memory](../elements/memory.md); silence re-ask for open `Question`s ([Question](../elements/memory.md#question)); Deploy catch-up; [repair row](../elements/memory.md#repair-row) observation; check that «TravelAgency CI/CD» and «Еженедельный аудит порядка» are enabled (missing or disabled = blocker reported to the owner, [routines](../elements/automations.md#routines-keep-enabled)) |
| Weekly audit | routine «Еженедельный аудит порядка», every Monday 12:00 Europe/Moscow | [weekly audit](weekly-audit.md), including open `Question`s (backstop if no other wake ran) |
| Owner message | owner chat | answer, instruction, stop |

On every wake, before new work: read [memory](../elements/memory.md), then run the [never-stall checks](../orchestrator.md#8-never-stall) **before** the safety-net “expected → sleep” branch. Before sleeping on any wake, perform every row whose `Waiting on` = `none`, whose `Question` = `-` and whose `Next` is a concrete step; a row with `Waiting on` = `issue #NN` resumes only when #NN closes (or at once if #NN is already closed); a row with a non-empty `Question` makes no column transition until the answer, except [Question guard](../elements/memory.md#question-guard) exceptions (a) and (b) ([Question](../elements/memory.md#question)). Do not invent another routine; align “next day” / silence re-ask with memory-refresh and Monday audit wakes only.

### Safety-net behaviour
Webhooks are **not** the primary driver of review or merge. The cloud agent owns CI and Automations on its PR until it reports ready ([orchestrator §5.8](../orchestrator.md#58-cloud-agents)).

On a CI/CD wake:
1. Match by sha / branch / PR to a memory row.
2. Run never-stall checks first (stalled agents, Deploy catch-up, rows with `Waiting on` = `none`). A CI/CD wake never sends another owner message about an open `Question`; re-asks happen only on memory-refresh and the Monday audit.
3. **Deploy to dev** completion (green or red): never slept; act by the [Deploy wait](#deploy-wait) and the event table.
4. **CI or Secret scan** on a PR whose row still has a live `Agent` run → expected; confirm nothing is off plan; leave the agent in place; sleep.
5. Anything else (no live agent, second branch, Dependabot, missed agent, red unowned CI, Secret scan red with no owner) → act by the rules below or ask the owner. **Never ignore a strange wake.**

### Deploy wait
Row changes on a Deploy (advance, non-product exit, rollback, delete) and the sha format are defined once in [memory](../elements/memory.md#row-lifecycle); this section says how to read a Deploy run.
- **Deployed sha (the single definition):** rows move only by the commit actually deployed, never by the run's head sha (a manual rollback run has the tip of `main` as head but deploys `rollback_sha`). The movement sha is the `deployed-sha` artifact of the latest successful «Deploy to dev» run on `main` (`gh run download <run id> -n deployed-sha`), or the memory [`Last deploy:`](../elements/memory.md#what-it-holds) sha when that run is the recorded one; the payload `deployed_sha` is only a hint that a read is due, and an empty payload alone never means advance nothing. Write `Last deploy:` only from a 40-hex sha just read this way, and only for a run id greater than the recorded one, so a late webhook for an older run (including a rollback run) never overwrites it. No successful run: advance nothing. A rollback to S contains only S and its ancestors.
- **Two sources, never mixed:** the **latest** run's conclusion detects a failure (red, or orphan `cancelled` below), which stops the queue and opens the repair; rows move only by the movement sha above. A latest successful run whose artifact is gone and whose sha was never recorded: advance nothing and re-run it once (same commit, [orchestrator §5.14](../orchestrator.md#514-server-and-dev)) to recreate the artifact; when that re-run cannot be started (the token cannot trigger workflows), record the [repair row](../elements/memory.md#repair-row) asking the owner to start it, the same row a failed Deploy uses; no second repair path. Only the resume condition in [repair](10-review-and-merge.md#repair-while-the-queue-is-stopped) restarts the queue; a non-red latest run does not.
- **Every Deploy wake** (green or red) also runs [repair row](../elements/memory.md#repair-row) observation when that row exists (not in the turn that created it).
- **Green Deploy:** apply the [row lifecycle](../elements/memory.md#row-lifecycle) to every row: `Deploy` rows whose match sha the deployed sha contains, and the rollback check on Приёмка rows and rows marked `rolled-back`. Remove `Queue:` when the movement sha is the repair commit or a descendant of it ([repair](10-review-and-merge.md#repair-while-the-queue-is-stopped)). Only feature, bug-feature, non-product and Dependabot rows wait on Deploy; an epic never does.
- **Red Deploy:** `Deploy` rows keep their wait. The failure is a defect on `main`: stop the queue and open or take the one repair in this wake ([repair](10-review-and-merge.md#repair-while-the-queue-is-stopped), [bugs](bugs.md)).
- **Catch-up:** on any wake (including memory-refresh and the Monday audit), a `Deploy` row whose match merge (`mergedAt` of that PR) is older than 60 minutes: read the latest «Deploy to dev» run on `main` and the movement sha once and act by the rules above (including removing `Queue:` when that movement sha is the repair commit or a descendant).

- **Idempotent:** act only when the step's outcome is not already recorded (acceptance comment not posted, merge not done). Two wakes for the same step do the step once.
- **`cancelled`** conclusion: ignore it only when a newer run of the same workflow on that branch exists («CI» cancels runs superseded by a newer push; a manually cancelled latest «CI» run with no newer run is non-green «CI» for that head sha). When the latest «Deploy to dev» on `main` is `cancelled` and no later run is queued or in progress, treat it as a failed Deploy (**Red Deploy** above).
- **Missing webhook secret:** the notify job fails visibly; ask the owner to set the secret (ask-first).
- The webhook payload is untrusted: never put secrets in prompts or comments.
- **Dependabot:** only a **green** CI wake on a `dependabot/*` PR records the review row; red Dependabot CI follows the unowned-red path ([events](#events)) and the PR becomes a review row only once its CI is green. The green CI wake records the row ([memory](../elements/memory.md#waiting-on-values) Dependabot shape) and polls Automations in the turn for up to 15 minutes. Done: `Waiting on` = `none`, `Next` = full review, review now. Not done: the row stays; the next memory-refresh, Monday audit or CI wake for that PR re-checks and switches it. Never merge before the switch ([dependencies](../elements/dependencies.md)).

## Events

| Event | Action |
|---|---|
| Cloud agent reports PR ready ([ready predicate](10-review-and-merge.md#ready-predicate)) | Full orchestrator review and merge gates ([review and merge](10-review-and-merge.md)). |
| Cloud agent finished text stage | [Deliverable review](../templates/agents/deliverable-review.md); publish accepted text same turn; advance FSM only after accept. |
| Cloud agent errored or asked a question | Every question ends the run with `RESULT blocked` (that finish wakes the orchestrator). Answer in that wake with a reply to the same agent, or relaunch per [never stall](../orchestrator.md#8-never-stall); owner-needed → pause in place with the `Question` and the blocked agent id; the mechanical wait and its `Next` stay ([row lifecycle](../elements/memory.md#row-lifecycle) Block). An open wait for an answer without finish = missed agent. |
| Safety-net: green CI or Secret scan on a PR whose agent run is live | Expected → sleep (after never-stall checks). |
| Safety-net: green CI on `dependabot/*` | Poll Automations in the turn up to 15 minutes; done → full review ([dependencies](../elements/dependencies.md)); not done → row stays `CI+Automations` for the next memory-refresh, Monday audit or CI wake on that PR. |
| Safety-net: CI or Secret scan red on a PR whose agent run is live | Expected that the agent fixes it; no live run (`Agent` cleared) → take over (reply to or relaunch the agent) or ask. |
| Safety-net: Deploy failed on `main` (or `cancelled` with no later run) | Stop the merge queue (memory `Queue:` line) and open or take the one repair in this wake, ahead of epic children: one re-run when nothing is broken, otherwise exactly one repair item whose PR is the only merge allowed ([repair](10-review-and-merge.md#repair-while-the-queue-is-stopped), [bugs](bugs.md)). A server change needs the owner's yes through the [repair row](../elements/memory.md#repair-row); a re-run of the same commit does not ([orchestrator §5.14](../orchestrator.md#514-server-and-dev)). |
| Safety-net: Secret scan on `main`, or CI / Secret scan whose sha is a row's `entry` or `fix` while that row is `Deploy` | Expected after merge → sleep after never-stall checks; no relaunch, no queue change. |
| Safety-net: unowned red CI on a PR (Dependabot, no live agent) | That PR does not merge; the queue is not stopped. Take over (reply to or relaunch the agent) or open or take a backlog item through the FSM ([bugs](bugs.md)). A Dependabot PR becomes a review row only once its CI is green ([dependencies](../elements/dependencies.md)). |
| Safety-net: green Deploy on `main` | Read the deployed sha ([Deploy wait](#deploy-wait)) and apply the [row lifecycle](../elements/memory.md#row-lifecycle) to every row (advance, non-product exit, rollback check, delete), subject to the [Question guard](../elements/memory.md#question-guard); check the queue resume condition ([repair](10-review-and-merge.md#repair-while-the-queue-is-stopped)). Never an epic row. |
| Safety-net: red Deploy on `main` | `Deploy` rows keep their wait ([Deploy wait](#deploy-wait)); stop the queue and open or take the repair (previous row). |
| Issue #NN closed | In the same turn resume every memory row with `Waiting on` = `issue #NN` ([done](../elements/board/columns/done.md)), subject to the [Question guard](../elements/memory.md#question-guard). |
| PR findings while agent owns the PR | Agent answers; orchestrator does not merge until the agent reports ready and full review passes. |
| `TA: Doc- after merge` on a merged PR | [Doc- after merge](12-docs-after-merge.md). |
| `TA: Weekly vuln scan` (Monday 09:00 MSK) | Read run history in the [weekly audit](weekly-audit.md); open backlog items for real findings. |
| New issue filed (by anyone) | Not itself a wake. On the next owner message or weekly audit: classify, bring to template, single `статус:*`, Status = Очередь, «Приоритет» ([intake](01-intake.md)). |
| Owner answer to an open question | The reply clears only the row's `Question` it answers ([Question](../elements/memory.md#question)); a reply that does not answer it keeps it. Record «**Итог:** решено: ...» on the issue and in «Решения», then re-evaluate the row and perform the pending transition if its condition still holds. `epic demo`: follows the [epic demo](13-epic-acceptance.md) (Готово only if the epic is still in Демо and every child is Готово; В работе plus new Очередь children on gaps). `create Status «Демо»`: once the option exists, set `статус: демо` / Status = Демо and run the epic demo in that turn if every child is still Готово. An answer on a `question` issue with no PR closes it ([non-product work](non-product-work.md)). The [repair row](../elements/memory.md#repair-row) ask is not cleared by a reply: on the owner's yes, in the same turn start `gh run rerun <run id>`, set `Queue: stopped since run <id>; repair: re-run <id>`, and leave the row until observation; do not re-ask or start a second re-run of that id; observation still ignores the causing attempt and deletes the row when the later new attempt succeeds or fails ([repair row](../elements/memory.md#repair-row)). Any other answer clears the `Question` and performs the pending step when it still holds, including the stage exit; when the cleared `Question` had an ` agent <id>` suffix, resume that run per the [Answer turn](../elements/memory.md#row-lifecycle) (set `Waiting on` = `agent` only while `Next` is still the reply; if a mechanical wait is still pending, reply and set `Agent` only, leave `Waiting on` and `Next`; never park a booked step by writing `agent` last). |
| Owner stop or long pause of an item or epic | Record in memory; for a work-stream stop set `статус: удержание` ([Удержание](../elements/board/columns/on-hold.md)); for an epic: cancel every child agent, move every open in-flight child to Удержание with its own restore column, clear «Приоритет» on its Очередь children. Memory row: `Question` = `hold: …`, `Next` = restore the recorded column after the resume word ([Question](../elements/memory.md#question)). The recorded resume turn clears `hold:` on every row whose resume condition was met — that item itself, or the epic plus each child named in the epic hold comment — restores those columns and «Приоритет», then restarts each restored row ([Question guard](../elements/memory.md#question-guard) exception (b), [Удержание](../elements/board/columns/on-hold.md)). |
| Defect found in the project | Code: [bugs](bugs.md). Docs vs code: fix wiki if code is right, else open an issue. Process drift: [orchestrator §6](../orchestrator.md#6-powers-act-and-report-vs-ask-first). Security: report and treat first. |

These events sit on the FSM; they do not replace owner epic acceptance in Демо.
