# 09 Development (column Разработка)
**Entry:** «Полное ТЗ» holds ([gates](README.md#gates)). Крупная with `Тесты: сначала сценарии` gets there through [Тест-кейсы](08-test-cases.md). Every other feature gets there from Очередь by [take](README.md#take). Do not enter, and do not keep coding, while a section is missing. An item already in Разработка when this rule set took effect keeps coding against the page it has; a missing new `Вид` or `Тесты` tag does not stop it, and an in-flight remap onto this column (open PR) does the same ([in-flight](README.md#gates)).

**Who:** one cloud agent and one PR: [developer brief](../briefs/developer.md) for application code and its tests; [devops brief](../briefs/devops.md) for workflows, Docker, nginx and deploy files. Launch per [cloud agents](../elements/cloud-agents.md) with the [launch brief](../templates/agents/launch-brief.md).

**Rules**
- Branch `type/NN-short-english-slug` created by the orchestrator with `gh issue develop` when it does not exist ([branches](../elements/git/branches.md)).
- Follow `Тесты` ([kind and test policy](05-epic-split.md#kind-and-test-policy)). `сначала сценарии`: write the tests first, then the code, in this same PR. Do not open a tests-only PR and do not fit tests to bad code. `поправить существующие`: adjust the named tests. `без новых`: add no new automated tests. A fragile test, including one tied to a calendar date, is forbidden; if a stable test cannot be written, omit it and say so. Implement the epic «Архитектура» for this slice. The feature input is the thin TZ. Add no product scope the epic «Ожидания» and the thin TZ did not justify. Do not add a feature architecture section. Stay on the epic's «Ожидания».
- A typo, or a 500 caused by a typo, inside this feature is fixed here; no new issue ([bugs](bugs.md)).
- Deviation needed: stop and raise a [question](../templates/agents/question.md) with a proposed «Решения» row. Do not code around the page. If the epic architecture does not cover a clean, secure solution, raise an [epic architecture gap](04-epic-architecture.md#gap) instead of a feature architecture section.
- PR per [pull requests](../elements/git/pull-requests.md): «Задача» `#NN` only, never `closes`/`fix`/`fixes`. «Документация» is «вики не затронута», or a page name. Малая also puts the `Doc-` draft text in that section; review checks it with the code. Крупная names the page and leaves the text for after merge. The developer does not publish the wiki. Commits per [commits](../elements/git/commits.md).
- The agent watches CI, Secret scan and Cursor Automations at the depth of the feature ([depth by size](../elements/automations.md#depth-by-size)), fixes red CI that belongs to this PR, answers bot findings, and only when the [ready predicate](10-review-and-merge.md#ready-predicate) holds marks the PR ready and reports with the [agent report](../templates/agents/agent-report.md) ([review and merge §1](10-review-and-merge.md#1-cloud-agent-until-ready)). A real smell is named in that report; the agent does not hunt for them.

**Output:** a PR ready for orchestrator review ([ready predicate](10-review-and-merge.md#ready-predicate)).

**Exit gate:** PR open into `main`, agent reported ready, «Документация» and «Задача» set; the label stays `статус: разработка` through the orchestrator full review and merge ([review and merge](10-review-and-merge.md)). After a green Deploy that contains the merge: a product item (feature, bug-feature) → Приёмка ([Приёмка](11-deploy-and-acceptance.md)); a non-product item per [non-product work](non-product-work.md).
